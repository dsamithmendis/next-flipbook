# Performance

What was measured on long PDFs, how, and what the numbers do not show. The benchmarks are in [`benchmarks/`](../benchmarks/README.md); run them to get figures for your own machine.

## In short

- **Memory does not grow with the length of the document.** Reading through a 1000 page PDF holds the same ten rendered pages, about 10 MB of canvas, as a 100 page one. At most four canvases are in the DOM at a time: the two pages showing, and up to two more while a turn is in flight.
- **Page turns stay at about 60 fps** at 100, 500 and 1000 pages, and the next pages are drawn by the time the animation ends. In a few runs a single frame took 50 to 180 ms; see [Slow frames](#slow-frames).
- **Time to first page does not depend on the length.** It was 0.83 to 0.90 s from the start of navigation at every size, from a local server.
- **Search cost is linear** in the number of pages (3 to 4 ms a page in the browser) and does not stall the page. Its index is bounded by `pdf.maxTextCacheBytes`.
- **Leaving the page leaves nothing behind**: no PDF.js worker, no canvas, no growth in DOM nodes or listeners over eight visits.
- **The thumbnail panel is the one part that grows with the length**: a button per page, about 3 DOM elements and one listener each. At 1000 pages that is 3000 elements and about 100 ms to open. See [the thumbnail panel](#the-thumbnail-panel).

## What it was measured on

| | |
| --- | --- |
| Machine | A shared sandbox with 2 CPUs and 8 GB of RAM, Linux, Node 22.22 |
| Browser | Headless Chromium 141, painting in software, window 1280 × 900 at device pixel ratio 1 |
| Software | `next-flipbook` 0.6.0, `pdfjs-dist` 6.3.289, a Next.js 16.3.7 production build of the demo |
| Documents | Generated by `benchmarks/lib/big-pdf.mjs`: dense pages of text with an outline, 100, 500 and 1000 pages (152 KB to 1.5 MB), served from localhost |
| Runs | One run of each figure unless said otherwise. A shared machine is noisy: treat differences of a few milliseconds as nothing |

Two benchmarks, because they see different things. `pipeline.mjs` runs the PDF code in Node, with PDF.js on the main thread and a native canvas, so it measures the work and the memory without a browser's compositor. `browser.mjs` drives the real demo in Chromium.

## In a browser

Each size opened in a fresh browser context: 40 page turns with 120 ms spent on each spread, 12 jumps to random pages, a search of every page for a word that is not there, then the thumbnail panel opened and scrolled end to end. Times are milliseconds unless stated.

| | 100 pages | 500 pages | 1000 pages |
| --- | --- | --- | --- |
| Document opened, from navigation start | 845 | 802 | 725 |
| First page drawn, from navigation start | 897 | 892 | 828 |
| Frame rate during page turns | 59.1 | 59.0 | 59.6 |
| Frame interval during turns, p95 | 16.8 | 16.8 | 16.7 |
| Pages still undrawn when the turn ends, p95 | 0.1 | 0.2 | 0.1 |
| Jump: requested page drawn, p50 / p95 | 45 / 56 | 42 / 56 | 46 / 73 |
| Jump: blank after the animation ends | 0 | 0 | 0 |
| Canvases in the page, peak | 4 | 4 | 4 |
| Page cache after reading | 10 pages, 10.4 MB | 10 pages, 10.4 MB | 10 pages, 10.4 MB |
| Page cache hit rate over the run | 91% | 91% | 91% |
| Search of every page | 348 | 1437 | 3663 |
| Search index | 1.4 MB | 7 MB | 14 MB |
| Longest frame while searching | 16.7 | 16.8 | 16.8 |
| Page heap after search (after forced GC) | 6.2 MB | 9.5 MB | 13.5 MB |

A 60 Hz frame is 16.7 ms. The jump numbers are from the call until the requested page has its picture; the turn animation takes longer than that (0.7 s and up), so the reader does not see an empty page.

The page's JavaScript heap after reading is 5.6 to 5.7 MB at every size. What grows with the length is the search index (14 KB a page for this text) and the thumbnail panel, below.

### Slow frames

Across 14 runs of 40 turns (a size is one run), the longest frame was 17 ms in two, 33 to 50 ms in four, and 67 to 183 ms in eight; in those, one to three of the 40 turns had a frame over 50 ms. They were single frames, not a drop in rate, and only one run had a long task (a main-thread task over 50 ms) during a turn: 57 ms. They were more common at 100 and 500 pages than at 1000, which is probably chance.

PDF.js cleanup (`cleanupAfterPages`) was the obvious suspect, so a separate probe logged the moment each cleanup was sent to the worker and every frame over 40 ms on the same clock, over five runs of 60 turns. Cleanups happened every 12 turns (turns 11, 23, 35, 47 and, in some runs, 59), and slow frames did not follow them: one slow frame in 300 turns, a 50 ms one at turn 59 of a run at 100 pages. The spikes did not repeat at the same turn between runs. The cause was not found, and it may be the shared sandbox rather than the library. The claim here is "about 60 fps, with an occasional single slow frame", not "no dropped frames".

### The thumbnail panel

Opening it makes one button for every page; only the buttons near the viewport draw a picture.

| | 100 pages | 500 pages | 1000 pages |
| --- | --- | --- | --- |
| DOM elements added | 309 | 1509 | 3009 |
| Event listeners added | 100 | 502 | 1008 |
| First button, then first picture | 15, 70 | 37, 107 | 104, 215 |
| Page heap added | 0.5 MB | 1.5 MB | 2.4 MB |
| Scrolled end to end in 80 steps: frame interval p95 / max | 33 / 83 | 33 / 50 | 33 / 100 |
| Pictures drawn at rest | 9 | 9 | 9 |
| Thumbnail cache after scrolling through all | 100 pictures, 6.5 MB | 160, 10.5 MB | 160, 10.5 MB |
| Frame rate turning pages with the panel open | 58.5 | 58.7 | 55.6 |

Pictures are limited to the ones near the viewport and to a cache of 160 (40 MB at most), however long the book is. The buttons are not: the cost of the panel grows linearly, and at 1000 pages it is noticeable only as a slightly slower open and a rougher scroll under software painting. The list is not windowed. If you ship books of several thousand pages, render the panel only when it is wanted (it costs nothing while closed), or build a windowed list from `useFlipBook()`; `FlipBookThumbnails` is exported so it can be used as the starting point. It was not built because nothing measured here needs it.

### Leaving the page

The cleanup check opens the long PDF by clicking a link, turns 8 pages, searches every page, and leaves by clicking another link, eight times. After each visit:

- no PDF.js worker was running (one while the book was open, none after) and no canvas was left;
- DOM nodes (308) and event listeners (407) were identical after every visit;
- the page heap rose by 0.033 MB a visit once warmed up, the same as a control page with no PDF in it (0.033 MB a visit). Over the eight visits the PDF page went from 6.2 to 7.0 MB and the control from 4.5 to 5.3 MB: the first few visits to any Next.js page add heap whatever it holds, which is why the check compares against a control.

The same properties are tested without a browser in `flipbook.cleanup.dom.test.tsx`, including under React `StrictMode` and for a book unmounted while its document is still loading.

### What changed in Phase 6

The same benchmark before and after, on the same machine. Before is the previous PDF session and manager code (0.5.0).

| | Before | After |
| --- | --- | --- |
| Pages drawn per page read, reading forward, `preloadPages` 8 with `cacheSize` 10 | 2.83 | 1.02 |
| The same, reading backward | 2.90 | 1.06 |
| Cache hit rate, reading forward, the same settings | 59.8% | 82.6% |
| JS heap after reading 100 spreads of a 1000 page PDF | 12.9 MB | 3.0 MB |
| JS heap after searching all 1000 pages | 47.2 MB | 15.0 MB |
| Rapid jumps (5 ms apart), p50 / p95, 1000 pages | 69 / 96 ms | 38 / 58 ms |
| Rapid jumps, 100 pages | 64 / 98 ms | 39 / 63 ms |
| Thumbnail pictures redrawn when the page turns, 300 pages | 600 | 8 or fewer |
| Thumbnail pictures redrawn when a bookmark is added, 300 pages | 300 | 2 or fewer |
| Opening the thumbnail panel at page 400 of 1000: pictures drawn | 44 | 9 |
| The same: pictures near the current page visible after | about 1.2 s | 0.1 to 0.3 s |

Before, a prefetch window larger than the cache drew pages and evicted them before they were seen, which is the first row. How much it wasted depended on timing: across runs of the old code it drew between 2.8 and 3.3 pages for every page read. It is the one way prefetching can waste work, so the window is now planned against the cache. The heap rows are the cost of what PDF.js keeps for every page it opens, which is now released when the reader is idle, and of how the text index was held. Search time is unchanged: 2.3 to 2.7 s for 1000 pages in both.

The thumbnail rows are counted in the tests (`flipbook.thumbnails.perf.dom.test.tsx`) except the last two, which are from the browser: the old list glided from the top to page 400, drawing every thumbnail it passed.

## What this does not show

- **Real hardware.** Headless Chromium paints in software. Absolute frame rates, and the cost of painting a turn, are not those of a laptop with a GPU or a phone. A phone is slower in every number here, and has far less memory to spend on canvases. Use `cacheSize` and `pdf.maxCacheBytes` to fit it.
- **Other browsers.** Safari, Firefox and iOS were not tested. Safari, on iOS especially, limits total canvas memory, which is why evicted canvases are shrunk to 0 × 0.
- **A real network.** The PDFs came from localhost. A real download adds to time to first page, and `pdf.documentParams` (`disableAutoFetch`, `rangeChunkSize`) change how a file is fetched; their effect was not measured.
- **Other documents.** These pages are text. Scanned pages, large embedded images and heavy vector art cost more to render and take more memory per page, so fewer fit in `pdf.maxCacheBytes`. The search index is about 14 KB a page for this text, so the 32 MB default holds roughly 2300 such pages before it drops the least recently used ones.
- **PDF.js's own memory.** The page heap excludes the PDF.js worker, and the resident-memory figures are noisy. The Node benchmark's resident growth, which includes PDF.js, is the better guide: about 85 MB at the peak, flat from 50 to 1000 pages.
- **Touch and print.** No real touch input, and no print dialog.
- **Statistics.** One run of each figure, on a shared machine. They say whether something is the right order of magnitude and whether it grows with the length of the document. They do not support a claim that one build is a few percent faster than another.

## Settings that matter

| Setting | Effect |
| --- | --- |
| `cacheSize` | How many rendered pages are kept. The prefetch window is cut to fit it, so raising `preloadPages` alone does nothing past it. |
| `pdf.maxCacheBytes` | A soft ceiling on canvas memory. Pages that would not fit are not prefetched. The visible pages are always drawn. |
| `preloadPages` | Pages prepared either side. 2 was enough to have the next spread drawn before the turn ended at every size here. |
| `pdf.maxConcurrentRenders` | Pages drawn at once. Not tuned here. |
| `pdf.maxTextCacheBytes` | How much search text is kept. Raise it for books you search often. |
| `pdf.cleanupAfterPages` | How many pages are opened before PDF.js is told to release its per-page memory when idle. `0` turns it off. |

`getCacheStats()` on the controller shows what is held while you tune these, and the `/large-pdf` demo shows it live.
